# Schema

This section describes the database collections used in the project, their main fields, relationships, and the constraints applied to the data.

---

## Implemented Mongoose collections (M01-M06)

### User — `backend/models/User.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated by MongoDB |
| `name` | String | Required, trimmed |
| `email` | String | Required, unique index, lowercased, trimmed |
| `password` | String | Required, minlength 6, `select: false` (excluded from query results by default) |
| `role` | String | Required, enum: `['INSTRUCTOR', 'LEARNER']` |
| `createdAt` | Date | Auto via `{ timestamps: true }` |
| `updatedAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:** unique index on `email` (enforced by Mongoose via `unique: true`).

**Note:** `password` has `select: false` — it will not appear in API responses unless explicitly selected with `.select('+password')`. Password hashing is handled during registration using bcrypt.

---

### Course — `backend/models/Course.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated |
| `title` | String | Required, trimmed |
| `description` | String | Required, trimmed |
| `category` | String | Required, trimmed |
| `status` | String | enum: `['DRAFT', 'PUBLISHED', 'ARCHIVED']`, default: `'DRAFT'` |
| `instructorId` | ObjectId | Required, ref: `'User'` |
| `createdAt` | Date | Auto via `{ timestamps: true }` |
| `updatedAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:**
- `{ status: 1 }` — filter by status (course discovery)
- `{ category: 1 }` — filter by category
- `{ instructorId: 1 }` — filter by instructor
- `{ createdAt: -1 }` — sort by creation date (newest first)

**Note:** Course status is managed through explicit state transitions rather than allowing arbitrary status changes. The supported flow is `DRAFT → PUBLISHED → ARCHIVED`, with `ARCHIVED → DRAFT` for restoration. Invalid transitions are rejected by the application layer.

### Lesson — `backend/models/Lesson.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated |
| `courseId` | ObjectId | Required, ref: `'Course'` |
| `title` | String | Required, trimmed |
| `content` | String | Default: `''` |
| `position` | Number | Required — determines lesson order |
| `createdAt` | Date | Auto via `{ timestamps: true }` |
| `updatedAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:**
- `{ courseId: 1, position: 1 }` — compound index; supports `GET /api/courses/:id/lessons` ordered query efficiently.

**Note:** Lesson order is stored using the `position` field. When a new lesson is created, its position is assigned automatically so lessons are returned in a predictable order.

### Enrollment — `backend/models/Enrollment.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated |
| `learnerId` | ObjectId | Required, ref: `'User'` |
| `courseId` | ObjectId | Required, ref: `'Course'` |
| `enrolledAt` | Date | Default: `Date.now` |
| `lastProgressAt` | Date | Default: `null` — updated when learner progress changes |
| `createdAt` | Date | Auto via `{ timestamps: true }` |
| `updatedAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:**
- `{ learnerId: 1, courseId: 1 }` — **unique compound index**; prevents duplicate enrollment for the same learner and course.
- `{ courseId: 1 }` — supports queries for enrollments belonging to a course.
- `{ lastProgressAt: 1 }` — supports queries based on recent learner progress.

---

### Progress — `backend/models/Progress.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated |
| `enrollmentId` | ObjectId | Required, ref: `'Enrollment'` |
| `lessonId` | ObjectId | Required, ref: `'Lesson'` |
| `completedAt` | Date | Default: `Date.now` |
| `createdAt` | Date | Auto via `{ timestamps: true }` |
| `updatedAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:**
- `{ enrollmentId: 1, lessonId: 1 }` — **unique compound index**; prevents recording the same lesson completion twice for the same enrollment.
- `{ completedAt: -1 }` — supports dashboard 8-week completions chart aggregation.

**Design note:** Progress status (`NOT_STARTED` / `IN_PROGRESS` / `COMPLETED`) is **derived at read-time** — never stored. It is calculated using the number of completed lessons compared with the total number of lessons in the course.

---

### ActivityLog — `backend/models/ActivityLog.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated |
| `courseId` | ObjectId | Required, ref: `'Course'` |
| `actorId` | ObjectId | Required, ref: `'User'` |
| `eventType` | String | Required, enum: `['COURSE_CREATED', 'COURSE_UPDATED', 'COURSE_PUBLISHED', 'COURSE_ARCHIVED', 'COURSE_RESTORED', 'LESSON_CREATED', 'LESSON_UPDATED', 'LESSON_DELETED', 'ENROLLMENT_CREATED', 'PROGRESS_UPDATED', 'COMMENT']` |
| `metadata` | Mixed | Default: `{}` — flexible JSON for event-specific context (e.g. comment text, changed fields) |
| `createdAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:**
- `{ courseId: 1, createdAt: -1 }` — compound index; supports paginated activity feed for a course in reverse-chronological order.

**Append-only:** Activity logs are created through the activity service. The
application provides no UPDATE or DELETE API endpoints for ActivityLog records,
and the frontend provides no way to modify or delete existing activity records.

The `ACTIVITY_EVENT_TYPES` array is also exported from this module so service code can import and use the constants.

---

### Alert — `backend/models/Alert.js`

| Field | Mongoose type | Constraints / notes |
|-------|--------------|---------------------|
| `_id` | ObjectId | Auto-generated |
| `enrollmentId` | ObjectId | Required, ref: `'Enrollment'` |
| `dismissedAt` | Date | Default: `null` — `null` means alert is active; set when instructor dismisses |
| `lastProgressAtWhenDismissed` | Date | Default: `null` — snapshot of `Enrollment.lastProgressAt` at dismissal time |
| `createdAt` | Date | Auto via `{ timestamps: true }` |
| `updatedAt` | Date | Auto via `{ timestamps: true }` |

**Indexes:**
- `{ enrollmentId: 1 }` — **unique index**; one alert document per enrollment.

**Reappearance logic:** At read-time, the alert service checks:
1. Is enrollment `IN_PROGRESS`?
2. Has `lastProgressAt` been idle for > 14 days?
3. If dismissed: is `Enrollment.lastProgressAt > Alert.lastProgressAtWhenDismissed`? → learner made progress after dismissal → a new idle period can trigger reappearance.

## Relationships

| Relationship | Type | How modelled |
|-------------|------|--------------|
| User → Course | One-to-many (instructor owns many courses) | `Course.instructorId` ref |
| Course → Lesson | One-to-many | `Lesson.courseId` ref |
| User ↔ Course | Many-to-many (via Enrollment) | `Enrollment` collection with unique `(learnerId, courseId)` |
| Enrollment → Progress | One-to-many (one enrollment, many lesson completions) | `Progress.enrollmentId` ref |
| Course → ActivityLog | One-to-many | `ActivityLog.courseId` ref |
| Enrollment → Alert | One-to-one (one alert record per enrollment) | `Alert.enrollmentId` with unique index |

## Constraints: database vs application code

**Database-level (Mongoose unique indexes):**
- `User.email` — unique index → duplicate email registration rejected at DB level
- `{ learnerId, courseId }` on Enrollment — unique compound index → duplicate enrollment rejected at DB level
- `{ enrollmentId, lessonId }` on Progress — unique compound index → duplicate lesson completion rejected at DB level
- `{ enrollmentId }` on Alert — unique index → one alert record per enrollment

**Application-level (implemented in M02-M06):**
- Password hashing and authentication — implemented in M02 using bcrypt and JWT
- Role-based access — implemented in M02 through authentication and authorization middleware
- Course state machine transitions — implemented in M03
- Publishing guard — implemented in M03; a course must have at least one lesson before publishing
- Course and lesson ownership — implemented in M03; instructors can only modify their own courses and lessons
- Enrollment rules — implemented in M04/M05; learners can self-enroll in published courses, instructors can enroll learners in their own courses or bulk-enroll learners, and duplicate or unauthorized enrollments are rejected

**Why the line is drawn here:** MongoDB does not provide traditional relational-style CHECK constraints across multiple documents. Business rules that depend on multiple documents or collections are therefore handled in the application layer.

## Deliberate denormalisation

None at MVP. Progress status is **derived at read-time** from Progress record counts — deliberately avoiding a stored `progressStatus` field on Enrollment which would create a second source of truth.

---

## What would break first at 100× the data

- `GET /api/courses` with search + filters — needs index on `Course.title` for text search (currently uses regex; a `$text` index would be needed at scale)
- `GET /api/alerts` — evaluates IN_PROGRESS enrollments to identify inactive learners. The `lastProgressAt` index helps reduce the cost of inactivity-related queries, but this could still become expensive at much larger scale
- Dashboard aggregations — `$group` pipelines on large Progress/Enrollment collections; `Progress.completedAt` and `Enrollment.courseId` indexes help
- ActivityLog feed — unbounded per course; would need cursor-based pagination at scale
